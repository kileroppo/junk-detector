# Junk-detector rebirth: dead code removal, bug fixes, test suite, and rules expansion

This change removes ~1,000 lines of dead code (plans system, dispatcher, multimodal extractor, unused ML training and similarity functions), fixes eight bugs across the scorer/API/config/dedup stack, adds a 90-test suite covering the core scoring pipeline, and expands the deterministic rules engine from ~30 to 201 keywords while adding 7-day result caching and LLM output validation.

The approach is conservative refactoring: no new architectural abstractions were introduced. The dead code was genuinely unreachable (verified by import-graph analysis). Bug fixes address real production failure modes (cost accumulation loss after fallback, `model_copy` without `deep=True`, missing timeout on LLM calls). The rules expansion and caching are additive features that reduce LLM cost for obvious content.

**Watch for:** The dedup-then-cache path in `app.py` duplicates hash logic and can return a stale `ScoreResult` with missing fields (confirmed). The `query_by_domain` SQL uses unescaped `LIKE` with user-provided domain strings, opening a minor wildcard-injection vector (confirmed). The deep health check leaks internal error messages to unauthenticated callers (confirmed). Output validation is asymmetric — catches "too perfect positive" but not "too perfect negative" splits (confirmed).

## High-level view

Dead code removal is clean. The `pipeline_stages.py` enrich_stage docstring still lists "similar_articles" in its `Adds:` section, which is now stale after removing that hydrator.

The bug fixes target real failure paths: the scorer now accumulates cost across primary+fallback calls correctly, `model_copy(deep=True)` prevents weight mutation across requests, and the API validates text length at the Pydantic layer. The LLM timeout fix referenced in the task description only manifests as `timeout=5.0` on the health-check LLM call in this diff.

The test suite covers scorer orchestration, rules, dedup, API, and pipeline — but omits the caching path in `scorer.py`, the output-validation branch, `query_by_domain`, and the dedup-fallthrough path in `app.py`.

The output validation catches degenerate LLM responses (all-100, all-0, perfect positive/negative split) but is asymmetric: the inverse "everything terrible" pattern bypasses it, and triggered rejections still expose the suspicious dimension values in the response body.

<details>
<summary>Issues (7)</summary>

1. **Dedup/cache path duplicates hash computation** — The `/score` endpoint in `app.py` (lines 149-172) recomputes `content_hash` using `hashlib.sha256` on the raw URL/text key, but the scorer's own cache uses `hashlib.sha256` on `content_text` (the extracted body). These will diverge for URL inputs. Unify hashing or remove the endpoint-level cache return in favor of the scorer's own cache.

2. **`query_by_domain` wildcard injection** — `LIKE '%{domain}%'` with no escaping of `%` or `_` in the domain string means a domain containing those characters (unlikely but possible) produces unexpected matches. Escape `%` and `_` in the domain before interpolation, or use `INSTR()` instead of `LIKE`.

3. **Deep health check leaks error details** — `GET /health?deep=true` returns the full exception string to any caller. For a public-facing API, this can leak model names, API hostnames, and credential validation messages. Return a generic "unreachable" message and log the detail server-side.

4. **Dedup cache returns no result on miss** — When `should_score_content` returns `False` in `app.py`, the code tries to fetch a cached DB result by `content_hash`. If the DB has no match (the dedup TTL hasn't expired but the DB record was deleted or never saved), the endpoint falls through without returning a response or raising an exception. This is a silent 500 or `None` serialization error.

5. **Output validation asymmetry** — The validation checks `all positive >= 98 and all negative <= 2` but not the inverse. A prompt injection that maxes out negative dimensions while zeroing positive ones bypasses the check. Additionally, triggered rejections still return the suspicious `dimensions` object in the response body.

6. **Startup key check is prefix-brittle** — The lifespan handler uses `primary_model.startswith("ollama")` to decide whether a cloud API key is required. Custom presets that proxy through Ollama but don't prefix the model name with "ollama" would incorrectly require an API key.

7. **Test coverage gaps** — No tests for: the `scorer.py` cache-hit path, the output-validation rejection branch, `query_by_domain`, the lifespan startup failure path, or the dedup-returns-cached-result path in `app.py`.

## Dedup-then-cache return path in `/score`

The `/score` endpoint has a two-layer dedup check: first `should_score_content()` (60-second TTL in-memory), then a DB lookup by `content_hash`. The hash computed at the endpoint level uses the raw `content_key` (URL string or request text), while the scorer's DB-level cache computes the hash from the *extracted content text*. For URL inputs, these will never match — the endpoint hashes `"https://example.com/article"` while the DB record stores the hash of the article body.

```python
# app.py line ~155
content_key = request.url or request.text or ""
content_hash = hashlib.sha256(hash_input.encode()).hexdigest()  # hash of URL string

# scorer.py line ~85
content_hash = hashlib.sha256(content_text.encode()).hexdigest()  # hash of body text
```

If `query_by_content_hash` returns `None` (dedup says "don't score" but no DB record exists), the endpoint falls through the `if cached:` block without returning anything or raising an error, then continues to extraction — which contradicts the dedup guard's intent. The endpoint will re-score the content despite the dedup check saying it shouldn't.

## `query_by_domain` wildcard injection and index ineffectiveness

```python
cursor = conn.execute(
    "SELECT overall_score FROM scores WHERE source_url LIKE ?",
    (f"%{domain}%",),
)
```

The `LIKE '%domain%'` pattern can't use the `idx_scores_source_url` B-tree index (leading wildcard defeats index seeks). The index addition in the migration is cosmetic for this particular query — it remains a table scan. The wildcard-injection risk: if `domain` contains `%` or `_`, the results will be broader than expected.

## LLM output validation asymmetry

The validation catches three degenerate patterns: all dimensions at 100, all at 0, and the "too-perfect positive" split (positive >= 98, negative <= 2). The inverse pattern is missing: `all(d <= 2 for d in positive_dims) and all(d >= 98 for d in negative_dims)` would catch prompt injections designed to produce maximally negative scores.

When validation triggers, the response returns `overall_score=50.0` and `confidence=0.1` but keeps the *original suspicious dimensions* in the body. A client parsing `dimensions` directly (ignoring the overall score and confidence signal) would see the injected values. Consider replacing dimensions with neutral defaults (all 50) when rejecting.

## Deep health check information exposure

```python
except Exception as e:
    return {"status": "degraded", "llm_status": "unreachable", "error": str(e)}
```

The full exception string from `litellm.acompletion` can include API base URLs, model identifiers, and authentication error details ("Invalid API key: sk-..."). Since `/health` has no authentication requirement, this is visible to anyone probing the endpoint.

## Test suite gaps

Notable untested paths:
- The `scorer.py` cache-hit path (7-day TTL check) — a test with a mocked `query_by_content_hash` returning a recent result would verify the early-return
- The output-validation branch (suspicious LLM output -> `validation_rejected`)
- The `query_by_domain` DB function
- The `app.py` dedup-returns-cached-result path (including the fall-through on cache miss)
- The lifespan startup failure (no key, non-ollama model)
