# Test coverage expansion from 39% to 76%

Nineteen new test files add 448 tests covering the dispatcher, thunder monitoring, side effects, storage, auth, preferences, pipeline stages, extractors, embeddings, fast classifier, platform profiles, and web UI. No production code was modified. The tests pushed line coverage from 39% to 76%.

**Watch for:** Heavy mocking in pipeline_stages tests means the core scoring flow isn't validated end-to-end (confirmed). The `test_thunder.py` `_poll_source` tests use sleep-based timing that may be flaky in slow CI environments (likely). The auth router tests patch at the wrong layer — mocking `AuthService` directly on the router module means route-level validation logic is only partially exercised (confirmed).

## High-level view

The dispatcher tests are the strongest batch: they exercise real `PriorityTaskQueue` ordering, real retry calculation math, and real model validation — all without mocking.

The thunder module tests exercise the actual `ThunderMonitor._deduplicate` logic, `FeedItem.from_rss_entry` parsing, and `RSSSource` conditional header mechanics. The timing dependency in `_poll_source` (sleeps 0.05–0.1s waiting for a background task) is the one flakiness vector.

The pipeline_stages tests mock every dependency — scorer, hydrators, fingerprinting, extractors — which means they verify *orchestration logic* (fallback chains, error propagation, metadata enrichment) without proving the stages work with real inputs. Integration gaps between stages are untested.

The preferences, auth, and router tests mock the service layer and test HTTP contract only. No integration path tests real DB + real auth + real scoring together.

## Thunder polling tests and sleep-based synchronization

`test_poll_source_puts_items_in_queue` creates a background `asyncio.Task` running `_poll_source`, then calls `await asyncio.sleep(0.05)` before cancelling the task and checking the output queue:

```python
task = asyncio.create_task(monitor._poll_source(mock_source))
await asyncio.sleep(0.05)
task.cancel()
```

This pattern relies on the event loop scheduling the `_poll_source` coroutine, completing one poll, and placing the item in the queue — all within 50ms. On a CI runner under load, this could time out. The `test_poll_source_deduplicates` variant uses 100ms and expects multiple iterations of a 10ms poll interval, compounding the timing sensitivity.

A more robust approach: wait on `queue.get()` with a timeout, which blocks deterministically until the item arrives rather than guessing how long to sleep.

## Pipeline stages test isolation vs coverage value

Every external call in `pipeline_stages.py` is mocked: `extract_from_text`, `extract_from_url`, `smart_extract`, `hydrate_source_reputation`, `hydrate_article_stats`, `find_similar`, `score()`, `_save_result`, `get_source_adjustment`, `save_fingerprint`. What the tests *do* verify:

- The fallback chain (processed_text → content.text → raw_input)
- Metadata enrichment logic (merging hydrator results)
- Error isolation (one hydrator failing doesn't block others)
- Postprocess adjustments (similarity penalties, source reputation labels, score clamping)
- Summarization fallback to truncation on LLM failure

These are the orchestration concerns. The tests would fail if someone changed the fallback order or broke the error-isolation pattern. They would *not* fail if `score()` started returning a different shape or `extract_from_text` changed its validation rules. That's the gap — silent breakage at module boundaries.

## Auth service bcrypt mock and drift risk

`test_auth_service.py` uses an `autouse=True` fixture that patches `_pwd_context` globally:

```python
mock_ctx.verify.side_effect = lambda password, hash_val: password == "securepass123"
```

If the production code changes how it calls `_pwd_context` (e.g., switching from `verify(password, hash)` to `verify_and_update(password, hash)`), these tests will still pass with the mock while the real code fails. Worth noting but not blocking given that bcrypt is well-encapsulated.

## Fast classifier loose assertions mask drift

`test_high_quality_content_classified_higher` asserts `predicted_score >= 50`, but the production `_rule_based_classify` returns exactly 70 for long, clean content. If someone accidentally changes the threshold or logic so it returns 55 instead, the test still passes. A tighter assertion (`>= 65`) would catch unintentional regressions while still leaving room for deliberate tuning.

Similarly, `test_scam_content_classified_as_junk` asserts `predicted_score < 30`, and the code returns 15 for heavy scam signals. These loose bounds reduce the tests' ability to catch partial breakage of the classifier.

## Import-patching fragility in extract_stage fallback test

`test_url_input_fallback_when_smart_extract_unavailable` patches `sys.modules` to simulate a missing playwright dependency:

```python
with patch.dict("sys.modules", {"src.extractors.playwright_web": None}):
    result = await extract_stage(url_ctx)
```

The production `extract_stage` does a try/except ImportError at the top of the function body. If the import is later refactored (e.g., moved to module level with a sentinel), this test will silently stop exercising the fallback. A better approach: mock `smart_extract` to raise `ImportError` directly, which tests the error path regardless of import structure.
